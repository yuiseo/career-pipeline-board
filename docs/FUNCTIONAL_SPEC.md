# 채용 파이프라인 보드 기능 명세

## 1. 문서 목적과 우선순위

이 문서는 채용 담당자가 지원자를 채용 단계별로 조회하고 이동·검색·필터링하는 SPA의 기능과 완료 조건을 정의한다. `DECISIONS.md`에서 확정한 결정을 기능·인수 조건 관점으로 정리한 문서이며, 새로운 결정을 만들지 않는다. 결정이 필요한 항목은 **(확정 필요)**로 표시한다.

요구사항이 충돌하거나 해석이 필요한 경우 다음 순서로 판단한다.

1. 과제 가이드의 Must 요구사항과 기술 제약 (원문은 저장소에 포함하지 않음)
2. `DECISIONS.md`에서 확정한 제품·기술 결정
3. `docs/PLAN.md`의 구현 순서와 완료 조건
4. `PROMPTS.md`의 설계 과정과 검증 기록
5. `CONTRIBUTING.md`의 작업·커밋 규칙

Must 기능을 먼저 완성한다. Should 기능은 Must의 동작과 데이터 정합성을 훼손하지 않는 범위에서 추가한다.

## 2. 제품 개요

### 2.1 사용자

- 주 사용자: 채용 담당자
- 사용 목적: 다수의 지원자를 단계별로 파악하고, 채용 진행 상황을 변경하며, 특정 지원자를 빠르게 찾아 상세 정보를 확인한다.

### 2.2 채용 단계

| 화면 표시 | 의미 |
|---|---|
| 서류검토 | 서류를 검토 중인 지원자 |
| 면접 | 면접을 진행 중인 지원자 |
| 처우협의 | 처우를 협의 중인 지원자 |
| 최종합격 | 채용이 확정된 지원자 |
| 불합격 | 채용 절차에서 탈락한 지원자 |

불합격은 중간 단계의 부가 상태가 아니라 독립된 컬럼이다. 보드의 기본 순서는 `서류검토 → 면접 → 처우협의 → 최종합격 → 불합격`이다.
`Stage`의 내부 문자열 식별자는 데이터 모델 구현 시 확정하되, 위 5개 값 외의 단계를 허용하지 않는다.

### 2.3 범위 우선순위

| 우선순위 | 범위 |
|---|---|
| Must | 보드·컬럼·카드, 단계 이동과 저장, 낙관적 업데이트와 실패 롤백, 이름 검색, 직무 다중 필터, 상세 패널, 로딩·에러·빈 상태, mock API 지연·실패 시뮬레이션, Must 기능 테스트(`docs/PLAN.md` 5단계) |
| Should | 빠른 연속 이동의 경쟁 상태 처리, 1,000건 가상 스크롤, Undo, Should 기능 추가 테스트, 키보드 접근성 |
| 범위 밖 | 지원자 생성·삭제·정보 수정, 인증·권한, 실제 백엔드, 서버 검색·페이지네이션, 드래그앤드롭(추후 발전 요건, DECISIONS 2-1) |

## 3. 데이터 명세

### 3.1 목록 데이터

보드와 카드가 사용하는 `CandidateSummary`는 다음 필드만 포함한다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | `string` | 예 | 지원자 식별자 |
| `name` | `string` | 예 | 지원자 이름 |
| `position` | `string` | 예 | 지원 직무 |
| `appliedAt` | ISO 날짜 문자열 | 예 | 지원일 |
| `stage` | `Stage` | 예 | 현재 채용 단계 |

### 3.2 상세 데이터

`CandidateDetail`은 목록 데이터의 모든 필드에 다음 정보를 추가한다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `email` | `string` | 예 | 이메일 주소 |
| `phone` | `string` | 예 | 연락처 |
| `experienceYears` | `number` | 예 | 경력 연차 |
| `education` | `string` | 예 | 학력 |

상세 정보는 읽기 전용이다.

## 4. Must 기능 명세

### FR-01. 보드·컬럼·카드

#### 동작

- 앱 진입 시 지원자 목록을 조회하고 5개 채용 단계 컬럼에 `stage`별로 분류해 표시한다.
- 각 컬럼 헤더에는 현재 검색·필터 조건을 통과한 지원자 수를 표시한다.
- 각 카드에는 이름, 직무, 지원일, 현재 단계를 표시한다.
- 단계가 변경되면 카드는 해당 단계의 컬럼에 표시되어야 한다.

#### 인수 조건

- [ ] 목록 조회 성공 시 모든 지원자가 정확히 하나의 컬럼에만 나타난다.
- [ ] 5개 컬럼이 정해진 순서와 한글 이름으로 표시된다.
- [ ] 카드의 네 필수 정보가 누락되지 않는다.
- [ ] 컬럼별 표시 수가 해당 컬럼의 필터 결과 수와 일치한다. (가상 스크롤 도입 후에도 DOM에 렌더링된 카드 수가 아니라 필터 결과 수를 기준으로 한다.)

### FR-02. 단계 이동과 영속 저장

#### 동작

- 카드의 명시적 단계 이동 액션을 열면 현재 단계를 제외한 다른 단계가 선택지로 나타난다.
- 사용자가 목적 단계를 선택하면 해당 지원자의 단계 변경 API를 호출한다.
- 성공 응답을 받으면 목록 캐시와 이미 조회된 상세 캐시의 `stage`를 서버 응답으로 갱신하고(TanStack Query), 성공 피드백(토스트)을 표시한다.
- 변경 결과는 브라우저 저장소에 유지되어 새로고침 후에도 동일해야 한다.
- 현재 표시 단계와 같은 단계로의 변경 요청은 생성하지 않는다.

#### 인수 조건

- [ ] 지원자를 모든 다른 단계로 이동할 수 있다.
- [ ] 성공한 이동은 새로고침 후에도 유지된다.
- [ ] 현재 단계는 이동 메뉴에서 제외된다.
- [ ] 같은 단계 선택에 대해 네트워크 요청이 발생하지 않는다.
- [ ] 이동 성공 시 성공 피드백이 표시된다.

### FR-03. 낙관적 업데이트와 실패 롤백

#### 상태 정의

- `confirmedStage`: 마지막 성공 응답 또는 목록 조회로 확인된 서버 단계. **별도로 저장하지 않고** TanStack Query 목록 캐시의 `stage`를 읽는다.
- `inFlightTarget`: 현재 API에 전송되어 응답을 기다리는 목표 단계. 지원자별 이동 상태 저장소에 저장하는 값이다. (DECISIONS 2-3: 저장 상태는 `inFlightTarget`, `pendingTarget`뿐이고 화면 단계는 파생값)
- 화면 표시 단계 우선순위: `inFlightTarget → confirmedStage`

#### 동작

1. 사용자가 새 단계를 선택하면 API 응답 전에 카드를 목적 컬럼으로 이동한다.
2. 요청 성공 시 응답의 단계를 확인된 상태로 반영하고 이동 중 상태를 해제한다.
3. 요청 실패 시 이동 중 상태를 버리고 마지막 `confirmedStage`로 카드를 복구한다.
4. 실패 사실과 재시도 방법을 사용자 피드백으로 표시한다.
5. Must 기준에서는 요청 중인 카드의 단계 이동 액션을 비활성화해 같은 지원자에 대한 동시 요청을 막는다.
6. 단계 변경 mutation은 자동 재시도하지 않는다.
7. 열린 상세 패널의 현재 단계도 카드와 같은 화면 표시 단계 규칙으로 계산한다.

#### 인수 조건

- [ ] 단계 선택 직후, 200~800ms 응답 지연 중에도 카드가 목적 컬럼에 보인다.
- [ ] 강제 실패 시 카드가 요청 전 확인된 컬럼으로 돌아간다.
- [ ] 실패 메시지에 다시 시도할 수 있는 액션이 있다.
- [ ] 실패 후 새로고침해도 실패한 목표 단계가 저장되어 있지 않다.
- [ ] 요청 처리 중 동일 카드에서 두 번째 요청을 만들 수 없다.
- [ ] 이동 실패가 다른 지원자의 상태에 영향을 주지 않는다.

### FR-04. 이름 검색과 직무 필터

#### 이름 검색

- 입력값과 실제 적용 검색어를 구분한다.
- 검색 버튼 클릭 또는 검색 입력에서 Enter를 누를 때만 검색어를 적용한다.
- 적용할 때 검색어 앞뒤 공백을 제거하고 이름의 부분 일치로 검색한다.
- 입력 중에는 기존 검색 결과를 유지한다.

#### 직무 필터

- 여러 직무를 동시에 선택할 수 있다.
- 체크 상태를 바꾸는 즉시 필터 결과에 반영한다.
- 선택한 직무끼리는 OR 조건으로 결합한다.
- 직무를 하나도 선택하지 않으면 모든 직무를 대상으로 한다.
- 이름 검색과 직무 필터는 AND 조건으로 결합한다.

#### URL과 초기화

- 적용된 이름 검색어는 `q`, 직무는 반복 가능한 `position` 쿼리 파라미터에 저장한다.
- 예: `?q=홍&position=frontend&position=backend`
- 조건 변경 시 `history.replaceState`를 사용해 불필요한 방문 기록을 만들지 않는다.
- 최초 진입과 새로고침 때 URL에서 조건을 복원한다.
- 필터 초기화는 검색어와 선택 직무를 모두 제거하고 전체 목록으로 복귀시킨다.

#### 성능 조건

- 목록은 최초 한 번 조회하고 검색·필터는 클라이언트에서 수행한다.
- 검색·필터 변경만으로 추가 목록 API 요청을 보내지 않는다.
- 200건 이상의 데이터에서도 사용자 입력과 필터 선택에 체감 지연이 없어야 한다.

#### 인수 조건

- [ ] 검색 버튼과 Enter가 동일한 결과를 만든다.
- [ ] 검색어 입력만 하고 적용하지 않으면 결과가 바뀌지 않는다.
- [ ] 앞뒤 공백을 제거한 이름 부분 검색이 동작한다.
- [ ] 직무 다중 선택 OR, 이름과 직무 AND 조건이 동작한다.
- [ ] 직무를 모두 해제하면 전체 직무가 표시된다.
- [ ] URL을 새로고침하거나 공유해도 같은 조건과 결과가 복원된다.
- [ ] 200건 이상에서 조건 변경 시 추가 네트워크 요청이 없다.

### FR-05. 지원자 상세 보기

#### 동작

- 카드를 클릭하면 현재 보드 맥락을 유지한 채 슬라이드 아웃 패널을 연다. 패널이 나오는 방향은 디자인 시안에서 정한다.
- 패널은 지원자 단건 API로 상세 정보를 조회한다.
- 이름, 직무, 지원일, 현재 단계, 이메일, 연락처, 경력 연차, 학력을 표시한다.
- 상세 요청의 로딩과 실패는 패널 내부에서 처리하며 보드 목록을 가리거나 에러 상태로 바꾸지 않는다.
- 상세 캐시가 있는 지원자를 다시 열 때는 TanStack Query 캐시를 활용한다.
- 열린 상세의 지원자를 이동하면 패널의 현재 단계도 보드와 일치해야 한다.

#### 인수 조건

- [ ] 카드 클릭 시 선택한 지원자의 패널이 열린다.
- [ ] 상세 로딩·에러가 보드 목록과 독립적으로 표시된다.
- [ ] 단계 이동 요청 중과 성공 후 모두 카드와 열린 상세의 단계가 일치한다.
- [ ] 패널을 닫아 보드로 돌아갈 수 있다.

### FR-06. 로딩·에러·빈 상태

#### 목록 로딩

- 최초 목록 조회 중에는 5개 컬럼 구조를 유지하는 스켈레톤을 표시한다.

#### 에러

- 목록 조회가 최종 실패하면 보드 영역에 오류 메시지와 다시 시도 액션을 표시한다.
- 조회 query는 일시적 실패를 위해 1회 자동 재시도한다.
- 상세 조회 실패는 상세 패널 안에서만 메시지와 다시 시도 액션을 표시한다.
- 단계 이동 실패는 FR-03의 롤백과 사용자 피드백을 따른다.

#### 빈 상태

| 상태 | 판별 조건 | 표시와 액션 |
|---|---|---|
| 전체 데이터 없음 | 원본 목록이 0건 | “등록된 지원자가 없습니다” |
| 검색·필터 결과 없음 | 원본 목록은 있으나 조건 적용 결과가 0건 | “조건에 맞는 지원자가 없습니다” + 필터 초기화 |
| 특정 컬럼 비어 있음 | 전체 필터 결과는 있으나 해당 단계가 0건 | 컬럼 내부에 “이 단계의 지원자가 없습니다” |

#### 인수 조건

- [ ] 로딩, 목록 에러, 세 종류의 빈 상태를 각각 재현할 수 있다.
- [ ] 목록 에러의 다시 시도 성공 시 보드가 표시된다.
- [ ] 검색·필터 빈 상태의 초기화 액션이 전체 목록을 복원한다.
- [ ] 한 컬럼이 비어 있어도 다른 컬럼의 카드는 정상 표시된다.

## 5. Mock API 명세

### 5.1 엔드포인트

| 메서드·경로 | 요청 | 성공 응답 |
|---|---|---|
| `GET /api/candidates` | 없음 | `CandidateSummary[]` |
| `GET /api/candidates/:id` | 경로의 지원자 ID | `CandidateDetail` |
| `PATCH /api/candidates/:id/stage` | `{ "stage": Stage }` | 변경된 `CandidateDetail` |

- 실패 응답은 HTTP 500과 `{ "message": string }` 형식을 사용한다.
- 존재하지 않는 지원자 ID는 `404`, 허용되지 않은 `stage` 값 등 잘못된 요청 본문은 `400`으로 응답한다. 응답 형식은 `{ "message": string }`로 같다. (DECISIONS 2-2)

### 5.2 지연·실패·저장

- MSW가 실제 HTTP 요청 경로를 가로채 mock API로 동작한다.
- 모든 API 요청은 200~800ms의 무작위 네트워크 지연을 거친다.
- 모든 API 요청은 기본 약 15% 확률로 실패한다.
- 기본 데이터는 고정된 결과를 생성하는 1,000건의 시드다.
- 데이터는 버전 키가 있는 localStorage에 저장한다. 저장 버전이 없거나 현재 버전과 다르면 시드를 다시 생성한다.
- PATCH는 성공이 확정된 경우에만 저장소를 변경한다.

### 5.3 개발 환경 시연 제어

| 쿼리 | 효과 |
|---|---|
| `mockFail=1` | API 실패 강제 |
| `mockFail=0` | API 실패 비활성화 |
| `mockSeed=0` | 전체 데이터 0건 상태 구성 |
| `mockReset=1` | 저장 데이터를 초기 시드로 재설정 |

시연 제어는 개발 환경에서만 동작하며 일반 검색·필터 쿼리와 함께 사용할 수 있어야 한다.

## 6. Should 확장 명세

### SR-01. 빠른 연속 이동 경쟁 상태 처리

- 요청 중 이동 메뉴를 활성화하고 지원자별 `pendingTarget`에 가장 최근 사용자 의도만 저장한다.
- 화면 표시 단계는 `pendingTarget → inFlightTarget → confirmedStage` 순서로 계산한다.
- 같은 지원자에 대한 네트워크 요청은 항상 하나씩 직렬로 전송한다.
- 진행 요청이 실패하면 `confirmedStage`로 복구하고 대기 의도를 버린다.
- 진행 요청 성공 후 대기 목표가 확인된 단계와 같으면 추가 요청 없이 이동 상태를 비운다.
- 서로 다른 지원자의 요청은 독립적으로 처리한다.

### SR-02. 1,000건 성능

- 컬럼별 가상 스크롤 등의 방식으로 1,000건에서 스크롤과 필터가 부드럽게 동작하도록 한다.
- 가상화로 카드가 언마운트되어도 단계 이동과 상세 선택 상태가 손실되지 않아야 한다.

### SR-03. Undo

> **(확정 필요)** Undo 설계는 DECISIONS에 아직 결정이 없다. 아래는 초안이며 `feat(undo)` 구현 전에 확정한다. 확정된 방향은 "되돌리기도 같은 이동 흐름(새 이동 의도)으로 처리"(docs/PLAN.md)뿐이다.

- 가장 최근에 성공한 단계 이동을 취소할 수 있다.
- Undo도 이전 값을 강제로 쓰는 별도 경로가 아니라 동일한 단계 이동 의도로 처리한다.
- Undo 실패 시 현재 확인된 서버 상태를 유지하고 사용자에게 알린다.

### SR-04. 테스트

- Must 기능 테스트(mock API 저장·실패, 단계 변경 성공·롤백, 검색·필터 조합, 상태 화면, 통합 시나리오)는 Must 범위이며 `docs/PLAN.md` 5단계 체크리스트를 따른다. DECISIONS 2-7에 따라 Must 기능을 모두 만든 뒤 `test(...)` 커밋으로 작성한다.
- 경쟁 상태를 구현했다면 연속 이동 성공, 첫 요청 실패, 후속 요청 실패, 중간 의도 덮어쓰기를 추가로 검증한다.

### SR-05. 웹 접근성

- 키보드만으로 카드 상세를 열고 닫으며 단계 이동 메뉴를 조작할 수 있다.
- 상세 패널이 닫히면 패널을 연 카드로 포커스가 돌아간다.
- 단계 이동 성공과 실패를 스크린 리더 사용자가 인지할 수 있게 알린다.

## 7. 상태 전이 기준

### 7.1 Must 단계 이동

| 이벤트 | 확인된 단계 | 이동 중 목표 | 화면 단계 | 후속 처리 |
|---|---|---|---|---|
| 초기 | 서류검토 | 없음 | 서류검토 | 없음 |
| 면접 선택 | 서류검토 | 면접 | 면접 | PATCH 전송, 이동 메뉴 비활성화 |
| 요청 성공 | 면접 | 없음 | 면접 | 목록·상세 캐시를 서버 응답으로 갱신, 성공 피드백 (저장소는 mock API가 변경) |
